# 宿主模型执行协议

默认由 WorkBuddy 当前会话模型撰写与自查，内置积分模型和自定义模型使用同一流程。脚本不代调宿主接口、不取内置凭据，也不读取可选 API 配置。宿主按所选模型正常计费，不承诺固定积分、调用次数或完成时长。

## 回执驱动

飞书任务使用 feishu deliver；本地输入用 generate。命令完成有限步骤后结束，不需要常驻服务器。

| 状态 | 宿主应做什么 |
| --- | --- |
| needs_model | 读取 model_task.task_file，按示例用文件写入工具保存 response_file，执行 next_command。 |
| continue_batch | 执行 next_command 继续剩余项目。 |
| completed | 查看逐项是否 archived，或是否达到用户指定的本地交付状态。 |
| needs_selection | 只询问缺少的表格、列、视图或材料选择，用原入口继续。 |
| incomplete / failed | 汇报已交付、缺项及失败；按错误码判断能否重试，不把部分成功说成全批成功。 |

next_command 已固定受管 Python、配置与项目。Windows PowerShell 使用 next_command，Windows Git Bash 使用 next_command_bash，不自行拼接解释器或脚本路径。正常任务无需再读 request_file、response_template，也不需要重复 doctor。任务文件已含字段示例；有 source_files 时须全部读取，工具提示截断则分段读完。

每次只做「读当前待办 → 写响应 → 提交」。不要探索源码、复制响应骨架再反复修改、编写临时校验器、批量填通过布尔值、轮询文件，或自己拼 Feishu 上传命令。没有可解决的下一步就反馈具体错误，不现场调试。

## 两项主要模型任务

### 1. 联合提炼与成稿（compose）

脚本解析 DOCX 或 PDF/OCR，保留完整原文和行政信息排除记录，不按固定页数截断。任务书原文编为 A1、A2，阶段总结编为 B1、B2；这些短编号只在当前项目有效，实际文件位置由脚本保管。

一次提交 plans、key_facts 和所有要求的报告。plans 拆解重要计划条件，使用 P1、P2，保留范围、节点与 A 来源；key_facts 只登记有来源的重要成果、数字及状态。正文段落为普通字符串，不填逐段事实类型、plan_ids 或 fact_ids。无需抄写每段原文，也无需维护事实和陈述哈希编号。

仍须读完相关材料，覆盖实质计划条件。当前成果来自 B 的实际进展；目标转述、下一步和前期基础不能代替本期成果。正文可自然连写「已完成 A，下一步 B」，只要状态清楚。数字、规格和认定口径不能混用。未来/总体计划保持参考范围；任务书版只写预期，不声称已完成。

履约、成果报告保持各自完整正文。两份均被要求时不能漏交。用户只要成果报告也要提炼相关计划和关键事实，不把履约审查一并强加给用户。

### 2. 重点核对（check）

程序汇集全部计划对照、全部出入点、关键事实、综合意见、重要数字与强结论，同组的不同表述均保留。任务附原材料上下文和报告概览；正常不再重复整篇成稿，也不按每个普通段落生成核对行。

核对对象、阶段、条件、规格、数量、完成状态、条件遗漏、两稿与卡片一致性。不得把「未说明」改成「未做」，不得把评测数量当通过率。尤其检查一处声称满足、一处又说必需交付物待确认的矛盾。只需返回实际读过的全部 K 编号和实质问题；无问题时 issues 为空。不要给几十个观点逐一输出 supported=true。

重点核对是同一模型自查，不宣称独立审计。材料真实性已经过人工程序确认，不调查输入或论文真实性。文风、少量重复、篇幅建议写 editorial_notes，不阻断出稿。长材料可能拆成若干核对分段，但不能略读或截断。

## 响应与字段修订

compose/check 的 UTF-8 JSON 外层为：

    {"request_id": "当前任务给出的编号", "result": {"按当前字段示例填写": "实际内容"}}

结构、来源或语义出现实质问题时，脚本只提供问题字段、允许修改的路径和相关材料。repair 的外层改为：

    {"request_id": "当前修订编号", "patches": [{"path": "/review/conclusion/0", "value": "该处修订后的完整文字"}]}

只提交反馈涉及的字段。数组下标从 0 开始；path 为给出的 JSON Pointer。不要返回 result、完整报告或修改无关内容；完整性缺失时可补对应的整个模块。程序合并后再检查和重点核对。明确不支持的语义意见必须先改正文，不能只重新填写通过。最多两轮实质修订、一次格式纠正，达到上限就保留诊断并继续其他项目。

## 材料、恢复与归档

下载后复用不可变本地材料快照，内部交接不反复请求飞书记录或重做 OCR。材料、任务文件、响应和成稿均有项目及版本绑定。归档前重新核对飞书输入是否变化；上传后仍下载回读附件并核对摘要，成功才标 archived。权限或材料发生变化时停止本项，不使用旧报告代替。

原文、计划与关键事实来源、全部正文、核对问题及修订记录保存在项目 _host/ 底稿。Word 末尾仅给少量主题与章节/页码，不列逐观点长表。仅任务书时出 forecast；已有总结读取失败不能当成材料缺失。只有 checked.json 确认的成稿才能归档；本地文件不等于已留档。

升级保留旧批次和文件，旧协议成稿不自动套用新检查；需重新生成的项目从新版入口开始，不手改 state、failed 或完成回执。不因宿主失败自动切换独立 API。

## 耗时口径

checked.json 的 material_seconds 为本地解析，core_validation_seconds 为程序内容检查，document_export_seconds 为排版导出。host_wait_seconds 是待办发布到响应提交的间隔，包含模型读写、宿主工具等待及人工停留，不能等同于 API 响应或 Python 校验。批次 download_seconds 累加材料下载/本地复用检查；preflight_seconds 仅为飞书清点，不是完整环境初始化时间。
